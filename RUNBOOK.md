# comp-report — runbook

Everything you do to this app after day one. Generated by the platform and kept
current by `insights upgrade-scaffold`, so it does not drift from the tooling.

---

## Make a change

```bash
uv sync                       # once, and after any dependency change
uv run insights doctor        # the same checks CI runs, run locally first
uv run insights run           # a job: run it now, exactly as the scheduler would
uv run insights up            # a web app: the whole local stack, behind the real edge
```

`doctor` and CI run **the same code**. If doctor is green and CI is red, that is a
platform bug — tell us, because the whole point of `doctor` is that it cannot
disagree.

### Test a web change

`insights up` starts the edge, the app and the console. Sign in by appending
`?as=you@corp.example` to the app's URL once; after that a session cookie carries it.

```bash
uv run insights logs --app comp-report             # what it did
uv run insights logs --app comp-report --startup   # why it did not boot
uv run insights connections --probe           # can it actually reach its systems
```

### Test a job change

```bash
uv run insights run
```

Exit codes are a contract: **0** succeeded · **1** the job broke · **2** the platform
refused it. The scheduler retries 1 and 2 differently, because a refusal will not fix
itself.

## Deploy

| Environment | How | Who approves |
|---|---|---|
| dev | every merge to `main` | nobody — it is automatic |
| uat | manual, from Actions | contributors |
| prod | manual, from Actions | owners |

The pipelines are in `.github/workflows/` and the platform owns them: they call a
central reusable workflow, and `insights upgrade-scaffold` updates them. Do not edit
them — your edits will be overwritten, and the version you are running is the version
CI enforces.

**Rolling back** is redeploying the previous image tag from Actions. Your Dockerfile
pins its base, so a rollback gets the image you actually had.

## Add a connection

1. Declare it in `app.yaml` under `connections:` — engine, host, and the **name** of a
   secret. Never the value: this file is in git, and a credential here is a credential
   in the history forever. The loader refuses one.
2. **Locally**, put the value in `.env` in this repo:

   ```
   my-warehouse-token=any-local-value
   ```

   `.env` is gitignored and CI refuses a committed one. Commit `.env.example`.
3. **In dev and prod**, your team writes it to `insights/comp-report/<secret-name>` in the
   secret store. The platform binds your app's identity to that path and **cannot
   read the value** — an explicit IAM Deny, not a promise. `.env` is not read outside
   local, so a stray one cannot become a production credential.
4. `uv run insights connections --probe` to check it works.

## When the platform ships a new SDK

> **0.2.0 adds the `mysql` engine and deprecates `Caller.has_role()`.** The old call
> keeps working until 1.0.0 and emits a telemetry record each time, so we can see the
> migration finish rather than assume it did. Use `require_role("reader")`.


Nothing breaks on its own. Your `uv.lock` pins the version you are on, so a release
reaches you when **you** re-lock:

```bash
uv lock --upgrade-package insights-sdk
uv run insights doctor
uv run insights run            # or `insights up`, and click through it
git commit -am "Upgrade insights-sdk"
```

Your `pyproject.toml` declares a **floor and a major bound** (`>=0.1,<1`), not a pin.
Patches and minors are picked up by re-locking; a breaking change means a new major,
which you opt into deliberately.

**The support window is N-2** — the current major plus the two before it. CI fails a
deploy whose SDK is outside it, so you find out at your desk and not on the day you
need to ship something urgent.

If a release deprecates something you use, you get a warning in your telemetry naming
the call, the replacement and the version it goes away in — before it goes away.

```bash
uv run insights upgrade-scaffold --check     # are the generated files current?
uv run insights upgrade-scaffold             # update them, then review the diff
```

## When something is wrong

| Symptom | First command |
|---|---|
| It will not start | `insights logs --app comp-report --startup` |
| It started, something is off | `insights logs --app comp-report` |
| A query is failing | `insights connections --probe` |
| Is it even deployed? | `insights status` |
| What has it been doing? | the console, at `/apps/console/` |

A connection error tells you **who fixes it**: an expired credential is yours, a TLS
or VPC routing failure is ours. If it says ours, tell us and paste the error.

## What you must not do

- **Do not edit `.github/workflows/`** — platform-owned, and overwritten on upgrade.
- **Do not put a credential in `app.yaml`** — CI refuses it, and git remembers anyway.
- **Do not commit `.env`** — CI refuses that too. `.env.example` is the committed one.
- **Do not run as root in your Dockerfile** — CI refuses it.
- **Do not add a second logger.** `get_logger()` refuses to emit a payload; a
  `logging.getLogger` beside it is an unenforced second path out of the process.

Everything else in this repo is yours, including your Python version.
